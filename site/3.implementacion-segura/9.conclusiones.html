    Conclusiones¶

    La implementación segura consiste en trasladar al código las decisiones tomadas durante el diseño y aplicar cada control en el punto donde realmente protege la aplicación.

    A lo largo del bloque hemos trabajado distintos mecanismos, pero todos responden a una misma idea:

    Los datos externos no deben controlar directamente el comportamiento de la aplicación.

    Un mismo principio en distintos contextos¶

    Los ejemplos vistos pueden resumirse así:

    Entrada de datos
    ↓
validar antes de utilizar

Salida HTML
    ↓
evitar que los datos se interpreten como código

Consultas SQL
    ↓
separar instrucciones y parámetros

Autenticación
    ↓
comprobar identidad en el servidor

Autorización
    ↓
comprobar permisos sobre cada operación

Archivos
    ↓
tratarlos como datos y controlar su almacenamiento

APIs
    ↓
validar, autenticar y autorizar cada endpoint

    Aunque los mecanismos técnicos cambien, la lógica permanece constante:

    dato externo
    ↓
control explícito
    ↓
uso seguro

    Cliente y servidor¶

    JavaScript puede ayudar a mejorar la experiencia del usuario:

    • validar formularios;
    • ocultar opciones no disponibles;
    • mostrar mensajes;
    • consumir APIs;
    • actualizar la interfaz.

    Pero las decisiones de seguridad deben comprobarse en el servidor.

    Por tanto:

    JavaScript mejora la experiencia. El servidor protege la aplicación.

    Este principio aparece en prácticamente todos los temas del bloque.

    Separar datos y código¶

    Una parte importante de la seguridad de implementación consiste en mantener separados los datos de las instrucciones que ejecuta la aplicación.

    Por ejemplo:

    XSS
datos ≠ HTML o JavaScript

SQL Injection
datos ≠ instrucciones SQL

Subida de archivos
archivos ≠ código ejecutable

    Cuando esta separación desaparece, un dato controlado externamente puede modificar el comportamiento previsto.

    Combinar controles¶

    Una aplicación segura no depende de una única comprobación.

    Por ejemplo, modificar una calificación puede requerir:

    Petición
   ↓
sesión válida
   ↓
datos válidos
   ↓
usuario autorizado
   ↓
consulta preparada
   ↓
actualización

    Cada control protege un aspecto diferente.

    Eliminar uno de ellos puede dejar una parte de la operación sin protección.

    No confiar en el cliente¶

    A lo largo del bloque hemos visto distintos datos que pueden ser modificados desde el navegador o mediante una petición construida manualmente:

    • identificadores;
    • roles;
    • precios;
    • notas;
    • nombres de archivo;
    • JSON;
    • campos ocultos;
    • parámetros de URL.

    La interfaz puede limitar lo que normalmente hace el usuario, pero el servidor debe asumir que la petición puede haber sido modificada.

    Analizar implementaciones vulnerables¶

    Los laboratorios con DVWA han permitido observar tres problemas concretos:

    • XSS;
    • SQL Injection;
    • subida insegura de archivos.

    El objetivo común no ha sido aprender a atacar una aplicación, sino seguir este proceso:

    observar
   ↓
identificar la causa
   ↓
corregir el código
   ↓
repetir la prueba

    Esta forma de trabajo resulta especialmente útil porque permite relacionar directamente una vulnerabilidad con una decisión concreta de desarrollo.

    Aplicación al reto¶

    Los principios del bloque deben trasladarse al proyecto desarrollado por cada equipo.

    Al implementar una funcionalidad conviene comprobar:

    ¿Qué datos recibe?

¿Quién puede enviar la petición?

¿Quién puede realizar la operación?

¿Cómo se utilizan esos datos?

¿Se muestran en HTML?

¿Se utilizan en SQL?

¿Se almacenan archivos?

¿Se devuelve información innecesaria?

¿La protección está realmente en el servidor?

    No todas las funcionalidades necesitan todos los controles.

    La seguridad consiste en aplicar el mecanismo adecuado al riesgo concreto.

    Antes del despliegue¶

    Con este bloque hemos trabajado principalmente la seguridad dentro del código de la aplicación.

    Sin embargo, una implementación correcta puede verse debilitada por una configuración insegura del entorno.

    Aspectos como:

    • HTTPS;
    • configuración del servidor web;
    • permisos;
    • variables de entorno;
    • secretos;
    • servicios expuestos;
    • acceso a la base de datos;
    • cabeceras de seguridad;
    • registros;

    forman parte de la siguiente fase.

    Por tanto, el siguiente paso será trasladar los mismos principios al entorno de despliegue.

    Ideas clave¶

    • Validar en el servidor toda entrada relevante.
    • Escapar la salida según el contexto.
    • Utilizar consultas preparadas.
    • Almacenar contraseñas con funciones específicas.
    • Gestionar sesiones de forma segura.
    • Autorizar cada operación en el servidor.
    • Controlar tipos, nombres y ubicación de los archivos.
    • Proteger todos los endpoints de una API.
    • No utilizar CORS como sustituto de autenticación o autorización.
    • Verificar que una corrección realmente elimina el comportamiento inseguro.
