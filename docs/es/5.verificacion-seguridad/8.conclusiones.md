# Conclusiones

La seguridad de una aplicación web no depende de una única técnica ni de una única herramienta.

A lo largo del módulo se ha trabajado como una propiedad transversal del desarrollo.

```text
Comprender

    ↓

Diseñar

    ↓

Implementar

    ↓

Desplegar

    ↓

Verificar
```

Cada fase aporta decisiones diferentes, pero todas forman parte del mismo proceso.

## Comprender antes de proteger

En el Bloque 1 se analizaron los elementos fundamentales de una aplicación web:

- navegador;
- servidor;
- protocolo HTTP;
- cookies y sesiones;
- HTTPS;
- herramientas de observación.

Comprender cómo circulan los datos permite identificar dónde deben aplicarse controles.

## Diseñar antes de programar

En el Bloque 2 se trabajó la seguridad desde el diseño.

Antes de escribir código deben plantearse preguntas como:

```text
¿Qué datos recibe la aplicación?

¿Qué usuarios existen?

¿Qué permisos necesita cada uno?

¿Qué información debe protegerse?

¿Qué errores pueden producirse?
```

Las decisiones tomadas en esta fase condicionan la implementación posterior.

## Implementar controles en el código

En el Bloque 3 se trasladaron esas decisiones a la implementación.

Se trabajaron controles relacionados con:

- validación;
- XSS;
- consultas preparadas;
- autenticación;
- autorización;
- sesiones;
- subida de archivos;
- APIs;
- CORS;
- secretos.

La idea principal fue que la seguridad debe formar parte de cada flujo funcional.

## Mantener la seguridad al desplegar

En el Bloque 4 se comprobó que una aplicación correctamente programada puede quedar expuesta por una configuración incorrecta.

Se trabajaron aspectos como:

- configuración de producción;
- HTTPS;
- variables de entorno;
- secretos;
- superficie de exposición;
- permisos;
- base de datos;
- cabeceras;
- errores;
- logs.

La seguridad del código debe mantenerse cuando la aplicación llega a producción.

## Verificar lo que se ha construido

En este bloque se ha completado el ciclo.

No basta con diseñar o implementar un control.

Debe comprobarse que funciona.

```text
Control previsto

        ↓

Implementación

        ↓

Prueba

        ↓

Resultado

        ↓

Evidencia
```

La verificación permite detectar diferencias entre lo que creemos que hace la aplicación y lo que realmente hace.

## Seguridad como proceso continuo

El desarrollo seguro no debería entenderse como una revisión final.

Es más eficaz cuando se incorpora al trabajo habitual:

```text
Desarrollar

    ↓

Revisar

    ↓

Probar

    ↓

Corregir

    ↓

Continuar
```

Este ciclo puede repetirse después de cada cambio importante.

## El papel de las herramientas

Durante el módulo se han utilizado herramientas como:

- Chrome DevTools;
- Burp Suite;
- DVWA;
- logs;
- `curl`.

La herramienta no es el objetivo.

Cada una sirve para observar o comprobar un comportamiento concreto.

```text
Pregunta

    ↓

Prueba

    ↓

Herramienta adecuada

    ↓

Evidencia
```

## Desarrollo seguro frente a pentesting

El enfoque del módulo ha sido siempre el desarrollo seguro.

No se pretende formar especialistas en pentesting.

El objetivo es que un desarrollador web sea capaz de:

- identificar riesgos;
- tomar decisiones seguras;
- aplicar controles;
- desplegar correctamente;
- verificar el resultado.

Conocer cómo puede manipularse una petición ayuda a programar mejor, pero siempre dentro de entornos propios, educativos o expresamente autorizados.

## Integración con los retos ETHAZI

La seguridad debe formar parte del propio reto.

No debe aparecer como una entrega aislada al final.

Puede integrarse mediante pequeñas evidencias:

- revisión de una funcionalidad;
- prueba negativa;
- captura de DevTools;
- petición modificada;
- checklist;
- revisión de despliegue;
- corrección aplicada.

El objetivo es que la seguridad acompañe al producto durante su desarrollo.

## De la afirmación a la evidencia

Una diferencia importante entre una aplicación simplemente desarrollada y una aplicación revisada es la capacidad de justificar las decisiones.

En lugar de afirmar:

> La autorización funciona.

podemos demostrar:

```text
Usuario A

        ↓

Solicita recurso de B

        ↓

HTTP 403
```

La evidencia permite convertir una decisión técnica en un resultado comprobable.

## Qué debería poder hacer el alumnado

Al finalizar el módulo, el alumnado debería ser capaz de:

- comprender los principales puntos de seguridad de una aplicación web;
- diseñar flujos teniendo en cuenta riesgos;
- validar datos en el servidor;
- generar salidas seguras;
- acceder a datos mediante mecanismos adecuados;
- implementar autenticación y autorización;
- gestionar sesiones y archivos de forma segura;
- proteger secretos;
- desplegar una aplicación con una configuración adecuada;
- revisar código;
- diseñar pruebas negativas;
- utilizar herramientas de observación y verificación;
- aplicar una checklist;
- aportar evidencias de seguridad.

## TxurdiGest como hilo conductor

TxurdiGest ha servido como referencia conceptual para aplicar los contenidos a una misma aplicación.

El objetivo no ha sido construir una solución cerrada.

Ha servido para plantear preguntas repetibles:

```text
¿Cómo recibe datos?

¿Cómo valida?

¿Cómo autentica?

¿Cómo autoriza?

¿Cómo accede a la base de datos?

¿Cómo se despliega?

¿Cómo se verifica?
```

Estas mismas preguntas pueden aplicarse a cualquier proyecto DAW.

## Cierre del módulo

Una aplicación web segura no es una aplicación sin errores.

Es una aplicación cuyo equipo:

- conoce sus riesgos;
- aplica controles razonables;
- limita la exposición;
- verifica los comportamientos importantes;
- corrige los problemas detectados.

La seguridad forma parte de la calidad del software.

## Idea final

> La seguridad no se añade al final del desarrollo. Se diseña, se implementa, se despliega y se verifica durante todo el ciclo de vida de la aplicación.
