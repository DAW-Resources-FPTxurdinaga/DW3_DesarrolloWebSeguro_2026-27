# Introducción a la verificación de la seguridad

La seguridad de una aplicación no termina cuando se implementa una medida de protección.

Después de diseñar, programar y desplegar una aplicación, es necesario comprobar que las medidas aplicadas funcionan como se esperaba.

```text
Decisión de seguridad

        ↓

Implementación

        ↓

Comprobación

        ↓

Resultado
```

La verificación convierte una suposición en una evidencia.

## Por qué verificar

Durante el desarrollo pueden aparecer errores aunque la intención sea correcta.

Por ejemplo:

- una validación puede aplicarse únicamente en el cliente;
- una comprobación de autorización puede olvidarse en una ruta;
- una consulta preparada puede sustituirse accidentalmente por una consulta construida manualmente;
- una variable de entorno puede no estar configurada en producción;
- un servidor puede mostrar errores internos aunque el código sea correcto.

Por tanto, la pregunta no debe ser únicamente:

> ¿Hemos aplicado una medida de seguridad?

También debe preguntarse:

> ¿Podemos comprobar que funciona?

## Verificación durante el desarrollo

La verificación no debería realizarse únicamente cuando la aplicación está terminada.

Debe incorporarse al ciclo normal de trabajo.

```text
Implementar

    ↓

Probar

    ↓

Revisar

    ↓

Corregir

    ↓

Continuar
```

Este enfoque permite detectar problemas cuando todavía son fáciles de corregir.

## Qué significa verificar

Verificar consiste en obtener una respuesta observable.

Ejemplo:

```text
Control esperado:
un usuario solo puede editar sus propios datos

        ↓

Prueba:
modificar el identificador del recurso

        ↓

Resultado esperado:
acceso denegado
```

La verificación no se basa en confiar en que el código parece correcto.

Se basa en observar el comportamiento real.

## Revisar desde distintos puntos de vista

Una misma funcionalidad puede revisarse desde diferentes perspectivas.

### Código

Comprobar cómo está implementada.

### Navegador

Observar peticiones, respuestas, cookies y cabeceras.

### Servidor

Comprobar configuración, permisos y logs.

### Usuario

Probar acciones válidas y no válidas.

La combinación de estos puntos de vista ofrece una visión más completa.

## Seguridad y pruebas funcionales

Las pruebas de seguridad están relacionadas con las pruebas funcionales.

Una prueba funcional puede preguntar:

```text
¿Puede un usuario crear una reserva?
```

Una prueba de seguridad puede añadir:

```text
¿Puede crearla con datos inválidos?

¿Puede modificar la reserva de otro usuario?

¿Puede realizar la operación sin autenticarse?
```

La funcionalidad y la seguridad deben comprobarse conjuntamente.

## Pruebas negativas

Las pruebas negativas comprueban que la aplicación rechaza correctamente determinadas acciones.

Ejemplos:

- credenciales incorrectas;
- parámetros fuera de rango;
- identificadores manipulados;
- archivos no permitidos;
- acceso sin permisos;
- métodos HTTP no esperados.

El resultado esperado no siempre es que la operación funcione.

En muchos casos, el resultado correcto es:

```text
Solicitud

    ↓

Validación o control

    ↓

Operación rechazada de forma segura
```

## Verificación manual y automatizada

Algunas comprobaciones pueden realizarse manualmente.

Por ejemplo:

- revisar una petición con DevTools;
- modificar un parámetro con Burp Suite;
- comprobar una cabecera HTTP;
- revisar una respuesta de error.

Otras pueden automatizarse mediante pruebas del proyecto.

El objetivo del módulo no es construir una infraestructura compleja de automatización, sino comprender que las comprobaciones importantes deben poder repetirse.

## Revisión entre iguales

Una revisión realizada por otra persona puede detectar problemas que el autor no observa.

```text
Desarrollador A

        ↓

Revisa código de B


Desarrollador B

        ↓

Revisa código de A
```

La revisión debe centrarse en decisiones concretas, no en opiniones generales sobre el código.

Por ejemplo:

- dónde se valida;
- dónde se autoriza;
- cómo se accede a datos;
- cómo se gestionan secretos;
- qué ocurre ante errores.

## Evidencia frente a opinión

Una afirmación como:

> La autorización está bien.

es difícil de evaluar.

Una evidencia es más útil:

```text
Petición realizada por usuario A

        ↓

Recurso perteneciente a usuario B

        ↓

Respuesta 403
```

La evidencia permite comprobar objetivamente el comportamiento de la aplicación.

## Aplicación a los retos DAW

En los retos, la verificación debe integrarse en el trabajo habitual.

No se trata de crear un informe independiente cada vez que se realiza una comprobación.

Puede bastar con:

- una captura;
- una petición;
- una respuesta;
- un fragmento de configuración;
- un checklist;
- una breve explicación.

La evidencia debe ser proporcional a lo que se quiere demostrar.

## Relación con los bloques anteriores

La verificación recupera contenidos de todo el módulo.

```text
Bloque 1

Comprender


Bloque 2

Diseñar


Bloque 3

Implementar


Bloque 4

Desplegar


Bloque 5

Verificar
```

Este último bloque no añade una nueva capa de seguridad.

Comprueba que las capas anteriores funcionan realmente.

## Idea clave

> Una medida de seguridad solo puede considerarse aplicada cuando podemos comprobar su comportamiento y aportar una evidencia de que funciona.
