# Actividad 2. Aplicación rápida al reto

## Situación

Antes de comenzar a desarrollar una aplicación conviene tener claro cómo se organizan sus principales componentes y qué comunicaciones se producirán entre ellos.

En esta actividad vais a trasladar los conceptos del bloque a vuestro propio reto.

## Tu trabajo

En equipo, revisad la aplicación que vais a desarrollar e identificad los siguientes elementos:

- cliente;
- servidor web;
- backend;
- base de datos;
- usuarios que accederán a la aplicación;
- punto en el que se gestionará la autenticación;
- punto en el que se mantendrá la sesión;
- comunicaciones que deberán realizarse mediante HTTPS.

Podéis representarlo mediante un esquema sencillo como este:

```text
Usuario
   ↓
Navegador
   ↓
Servidor web
   ↓
Aplicación
   ↓
Base de datos
```

Adaptad el esquema a vuestro proyecto.

## Algunas preguntas para orientar el análisis

No es necesario responderlas por escrito. Utilizadlas para comprobar que vuestro diseño tiene sentido.

- ¿Qué componentes estarán directamente accesibles desde Internet?
- ¿Qué componentes deberían quedar protegidos detrás del servidor?
- ¿Dónde se comprobará la identidad del usuario?
- ¿Dónde se almacenará la información de sesión?
- ¿Qué datos circularán entre el navegador y el servidor?
- ¿Qué información debería viajar siempre cifrada?
- ¿La base de datos necesita ser accesible directamente desde el navegador?

!!! warning "Evita este diseño"

    El navegador no debería acceder directamente a la base de datos ni asumir responsabilidades que corresponden al servidor.

## Cuando terminéis

El equipo debería ser capaz de explicar, en uno o dos minutos, cómo funciona la aplicación desde que un usuario accede con el navegador hasta que se consulta o modifica información en la base de datos.

No es necesario entregar un documento adicional. El esquema podrá reutilizarse y modificarse durante el desarrollo del reto.

## Objetivos

Al finalizar esta actividad serás capaz de:

- Identificar los principales componentes de una aplicación web.
- Diferenciar las responsabilidades del cliente, servidor y base de datos.
- Comprender la importancia de separar responsabilidades dentro de una aplicación.
- Relacionar las decisiones de arquitectura con la seguridad del sistema.

## Contexto

Un centro educativo quiere desarrollar una aplicación web para gestionar diferentes procesos académicos y administrativos.

La aplicación debe permitir:

- Gestionar usuarios.
- Consultar información académica.
- Almacenar datos.
- Gestionar documentos.
- Proteger información privada.

El equipo de desarrollo debe decidir cómo organizar técnicamente la aplicación.

Durante el análisis inicial aparece una pregunta importante:

> ¿Debe toda la lógica de la aplicación estar en un único lugar o es mejor separar responsabilidades?

La decisión tomada tendrá consecuencias en aspectos como:

- mantenimiento;
- escalabilidad;
- seguridad.

## Ejemplo guiado

Una aplicación web básica está formada por diferentes componentes:

```
Usuario

   ↓

Navegador web

   ↓

Servidor web

   ↓

Aplicación

   ↓

Base de datos
```

Cada componente tiene una responsabilidad diferente.

### Cliente

El navegador se encarga principalmente de:

- Mostrar la interfaz.
- Recoger la interacción del usuario.
- Enviar peticiones al servidor.

### Servidor

El servidor se encarga de:

- Recibir peticiones.
- Ejecutar la lógica de la aplicación.
- Aplicar reglas de negocio.
- Controlar permisos.

### Base de datos

La base de datos permite:

- Almacenar información.
- Consultar datos.
- Mantener la información de la aplicación.

Una aplicación segura debe establecer claramente qué responsabilidades corresponden a cada componente.

## Ejemplo aplicado a TxurdiGest

Un profesor accede a TxurdiGest para consultar las calificaciones de su grupo.

El proceso podría ser:

1. El profesor abre la aplicación desde el navegador.
2. El navegador envía una petición al servidor.
3. La aplicación comprueba la identidad del usuario.
4. El sistema verifica si tiene permisos para consultar esas calificaciones.
5. La aplicación consulta la información necesaria en la base de datos.
6. El servidor devuelve la respuesta al navegador.

Cada componente participa en el proceso:

| Componente | Responsabilidad | Aspecto de seguridad |
|-----------|-----------------|----------------------|
| Navegador | Mostrar información e interactuar con el usuario | No confiar en los datos recibidos del cliente |
| Servidor web | Gestionar las peticiones | Configuración segura |
| Aplicación | Aplicar reglas y permisos | Validación y autorización |
| Base de datos | Almacenar información | Protección de datos |

Una decisión importante es recordar que el navegador no es un entorno de confianza.

Aunque una aplicación utilice validaciones en el cliente para mejorar la experiencia de usuario, el servidor debe comprobar siempre la información recibida.

## Actividad individual

Analiza los siguientes diseños:

### Diseño A

Toda la lógica de la aplicación se ejecuta en el navegador.

El navegador:

- obtiene los datos;
- valida la información;
- decide qué puede hacer cada usuario.

### Diseño B

El navegador muestra la información y envía peticiones al servidor.

El servidor:

- valida los datos;
- comprueba permisos;
- accede a la base de datos.

Responde:

1. ¿Qué diseño es más seguro?
2. ¿Qué problemas puede tener el Diseño A?
3. ¿Qué responsabilidades deberían mantenerse siempre en el servidor?

## Aplicación en el reto

Durante el desarrollo de la aplicación del reto, el equipo deberá tomar decisiones relacionadas con la arquitectura antes de comenzar la implementación.

Antes de programar, el equipo debería definir:

### Componentes principales

Identificar:

- Qué parte de la aplicación se ejecutará en el cliente.
- Qué lógica se ejecutará en el servidor.
- Qué información almacenará la base de datos.

---

### Responsabilidades

Definir claramente:

- Qué tareas realiza el frontend.
- Qué operaciones controla el backend.
- Qué información gestiona la base de datos.

---

### Decisiones de seguridad

Durante el diseño del proyecto se deberá analizar:

- Qué información nunca debe confiarse al cliente.
- Qué comprobaciones debe realizar siempre el servidor.
- Qué datos necesitan protección.
- Qué usuarios podrán acceder a cada recurso.

Estas decisiones deberían quedar reflejadas en la documentación técnica del proyecto y revisarse durante el desarrollo.

---

## Errores habituales

Algunos errores frecuentes son:

- Confiar en las validaciones realizadas únicamente en JavaScript.
- Pensar que ocultar una opción en la interfaz impide acceder a ella.
- Mezclar toda la lógica de la aplicación en un único componente.
- No definir responsabilidades claras entre cliente y servidor.
- Permitir que el cliente controle decisiones relacionadas con permisos.

---

## Para recordar

- Una aplicación web está formada por diferentes componentes.
- Cada componente tiene responsabilidades concretas.
- La arquitectura influye directamente en la seguridad.
- El cliente no debe considerarse un entorno de confianza.
- Las decisiones importantes de seguridad deben tomarse antes de implementar la aplicación.
