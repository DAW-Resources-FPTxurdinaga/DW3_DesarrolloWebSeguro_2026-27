# Introducción a la implementación segura

Diseñar una aplicación de forma segura no es suficiente. Las decisiones tomadas durante el análisis y el diseño deben trasladarse correctamente al código.

En este bloque nos centraremos en esa fase: **implementar mecanismos de seguridad dentro de una aplicación web**.

El objetivo no es añadir controles al final del desarrollo, sino incorporar la seguridad mientras se programan formularios, consultas a base de datos, sesiones, permisos, cargas de archivos o APIs.

## Del diseño al código

En el bloque anterior se definieron decisiones como:

- qué datos deben validarse;
- cómo deben gestionarse los errores;
- quién puede autenticarse;
- qué acciones puede realizar cada usuario;
- qué información debe mantenerse fuera del código fuente.

Ahora esas decisiones deben convertirse en código.

Por ejemplo, decidir que una nota debe estar comprendida entre 0 y 10 no protege la aplicación por sí mismo. La implementación debe comprobar realmente esa condición antes de aceptar el dato.

```text
Diseño
    ↓
Definir la regla

Implementación
    ↓
Aplicar la regla en el código

Verificación
    ↓
Comprobar que realmente funciona
```

## Cliente y servidor no tienen la misma responsabilidad

En una aplicación web parte del código se ejecuta en el navegador y parte en el servidor.

Ambos pueden realizar comprobaciones, pero no ofrecen el mismo nivel de protección.

JavaScript puede utilizarse para mejorar la experiencia del usuario:

- detectar campos vacíos;
- comprobar formatos;
- mostrar mensajes inmediatos;
- deshabilitar opciones de la interfaz.

Sin embargo, el navegador está bajo el control del usuario. El código JavaScript puede modificarse, desactivarse o evitarse completamente enviando una petición HTTP por otros medios.

Por este motivo, las comprobaciones necesarias para proteger la aplicación deben realizarse siempre en el servidor.

!!! tip "Idea clave"

    **JavaScript mejora la experiencia del usuario. El servidor protege la aplicación.**

Esta diferencia aparecerá continuamente a lo largo del bloque.

## Implementar de forma segura no significa añadir más código

Una implementación segura no consiste necesariamente en escribir muchas comprobaciones.

Consiste en utilizar correctamente los mecanismos disponibles:

- validar los datos en el lugar adecuado;
- escapar la salida cuando sea necesario;
- utilizar consultas preparadas;
- almacenar contraseñas mediante funciones específicas;
- comprobar permisos antes de ejecutar operaciones;
- controlar los archivos recibidos;
- configurar correctamente las APIs.

En muchos casos, una pequeña decisión de implementación evita una vulnerabilidad importante.

## Aprender también a partir del código vulnerable

Durante este bloque analizaremos algunos ejemplos deliberadamente inseguros.

El objetivo no será aprender técnicas de ataque, sino comprender qué decisión de desarrollo provoca el problema y cómo debe corregirse.

El proceso será siempre similar:

```text
Código vulnerable
        ↓
Observar el problema
        ↓
Comprender la causa
        ↓
Corregir la implementación
        ↓
Comprobar el resultado
```

Para algunos de estos análisis utilizaremos **DVWA (Damn Vulnerable Web Application)**, una aplicación creada específicamente para trabajar con vulnerabilidades en un entorno controlado.

DVWA se utilizará únicamente cuando permita comprender mejor una implementación incorrecta. No será el centro del bloque ni sustituirá al desarrollo seguro de nuestras propias aplicaciones.

## Aplicación al proyecto

Los ejemplos del manual utilizarán **TxurdiGest** como caso de estudio, pero los principios deben trasladarse al proyecto desarrollado por cada equipo.

Cuando aparezca un mecanismo de seguridad, la pregunta importante será:

> **¿Dónde aparece este mismo problema en nuestra aplicación y cómo debemos resolverlo?**

De esta forma, el bloque no se limita a estudiar vulnerabilidades aisladas, sino que convierte cada concepto en una decisión concreta de implementación.

## Resumen

- La seguridad diseñada debe trasladarse correctamente al código.
- El navegador ayuda al usuario, pero no debe considerarse una barrera de seguridad.
- El servidor realiza las comprobaciones definitivas.
- Analizar código vulnerable permite comprender mejor cómo corregir una implementación.
- Cada mecanismo de seguridad debe aplicarse en el punto adecuado de la aplicación.
