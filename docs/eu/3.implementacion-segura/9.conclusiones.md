# Ondorioak

Inplementazio segurua diseinu fasean hartutako erabakiak kodean transferitzea da, eta kontrol bakoitza aplikazioa benetan babesten duen puntuan ezartzea.

Bloke honetan hainbat mekanismo landu ditugu, baina guztiak ideia berari erantzuten diote:

> **Kanpoko datuak ez dute aplikazioaren portaera zuzenean kontrolatu behar.**

## Printzipio bera testuinguru ezberdinetan

Ikusitako adibideak honela labur daitezke:

```text
Datu-sarrera
    ↓
erabili aurretik balidatu

HTML irteera
    ↓
ezikusi datuak kode gisa interpretatzea

SQL kontsultak
    ↓
datuak eta parametroak bereizi

Autentifikazioa
    ↓
identitatea zerbitzarian egiaztatu

Baimenak
    ↓
eragiketa bakoitzerako baimenak egiaztatu

Fitxategiak
    ↓
datu gisa tratatu eta biltegia kontrolatu

APIak
    ↓
endpoint bakoitza balidatu, autentikatu eta baimendu
```

Mekanismo teknikoak aldatu arren, logika konstantea mantentzen da:

```text
kanpoko datua
    ↓
kontrol esplizitua
    ↓
erabilera segurua
```

## Bezeroa eta zerbitzaria

JavaScript-ek erabiltzailearen esperientzia hobetzen lagun dezake:

- formularioak balidatu;
- ez dauden aukerak ezkutatu;
- mezuak erakutsi;
- APIak kontsumitu;
- interfazean eguneraketak egin.

Baina segurtasun-erabakiak zerbitzarian egiaztatu behar dira.

Beraz:

> **JavaScript-ek esperientzia hobetzen du. Zerbitzariak babesten du aplikazioa.**

## Datuak eta kodea bereizi

Inplementazio-segurtasunaren zati garrantzitsu bat datuak aplikazioak exekutatzen dituen instrukzioen eta kodearen artean bereiztea da.

Adibidez:

```text
XSS
datuak ≠ HTML edo JavaScript exekutagarri

SQL Injection
datuak ≠ SQL instrukzioak

Fitxategi-karga
fitxategiak ≠ kode exekutagarria
```

## Kontrolak konbinatu

Aplikazio segurua ez da kontrol bakar baten mende.

Adibidez, kalifikazio bat aldatzeak honakoak behar ditzake:

```text
Eskaera
   ↓
saio baliozkoa
   ↓
datuak baliozkoak
   ↓
erabiltzailea baimendua
   ↓
kontsulta prestatua
   ↓
eguneratzea
```

## Ez fidatu bezeroari

Bloke osoan nabigatzailetik edo eskuz eraikitako eskaeratik alda daitezkeen hainbat datu ikusi ditugu:

- identifikatzaileak;
- rolak;
- prezioak;
- notak;
- fitxategi-izenak;
- JSON;
- ezkutuko eremuak;
- URL parametroak.

Interfazea erabiltzaileari ikusgai dauden aukerak mugatu ditzake, baina zerbitzariak eskaera aldatu dela suposatu behar du.

## Ahultasun-implementazioak aztertzea

DVWA-ko laborategiek hiru arazo konkretu ikusteko aukera eman digu:

- XSS;
- SQL Injection;
- fitxategi-karga ez-segura.

Helburu komuna ez da aplikazioa erasotzea izan, baizik eta honako prozesua jarraitzea:

```text
behatu
   ↓
identifikatu arrazoia
   ↓
zuzendu kodea
   ↓
errepikatu proba
```

## Erronkaari aplikatzea

Blokeko printzipioak talde bakoitzaren proiektuari transferitu behar zaizkio.

Funtzionalitate bat inplementatzerakoan komeni da galdetu:

```text
Zein datu jasotzen ditu?

Nor bidal dezake eskaera?

Nor eragin dezake eragiketa?

Nola erabiltzen dira datu horiek?

HTML-n erakusten al dira?

SQL-en erabiltzen al dira?

Fitxategiak gordetzen al dira?

Informazio gehiegi itzultzen al da?

Babesa benetan zerbitzarian dago?
```

Ez dira funtzionalitate guztiek kontrol guztiak behar.

Segurtasuna arrisku konkretuari dagokion mekanismoa aplikatzea da.

## Deskargaren aurretik

Bloke honetan aplikazioaren kode barruan egindako segurtasunari buruz lan egin dugu.

Hala ere, inplementazio zuzena ere ingurunearen konfigurazio ez-seguruekin ahuldu daiteke.

Ahalgaiak bezalakoak:

- HTTPS;
- zerbitzari web-aren konfigurazioa;
- baimenak;
- ingurune-aldagaiak;
- sekretuak;
- erakusten diren zerbitzuak;
- datu-basearen sarbidea;
- segurtasun-barrak;
- erregistroak;

hurrengo fasearen parte dira.

Beraz, hurrengo urratsa **deskargaren ingurunearen** barruan printzipio berberak transferitzea izango da.

## Funtsezko ideiak

- Balidatu zerbitzarian sarrera garrantzitsu guztiak.
- Ihes egin irteera testuinguruaren arabera.
- Erabili kontsulta prestatuak.
- Gorde pasahitzak funtzio espezifikoekin.
- Kudeatu saioak modu seguruan.
- Baimendu eragiketa bakoitza zerbitzarian.
- Kudeatu fitxategien motak, izenak eta kokapena.
- Babestu APIaren endpoint guztiak.
- Ez erabili CORS autentifikazio edo baimenen ordezko.
- Egiaztatu zuzenketak benetan ahultasuna ezabatu duela.
